# PostgreSQL architecture and operations

## Sources of truth

PostgreSQL constraints are the durable integrity boundary. Redis is used only
for cache, rate limiting and coordination; S3 remains the binary-media store.

| Domain | Source tables | Derived/materialized data |
| --- | --- | --- |
| Users | `users` (paid plans were retired in migration 012; their data is archived in `legacy_billing_archive`) | User counters and quota state |
| Exercises | `exercises`, secondary-muscle and instruction tables | Cached list/detail responses |
| Training | `routines`, `workouts`, exercise/set child tables | Daily stats and personal records |
| Social graph | `user_follows`, `connections` | User follower/following/connection counters |
| Posts and stories | `posts`, `post_media`, likes/comments, `stories`, `story_views` | Interaction/view counters |
| Messaging | `conversations`, participants, `messages` | Unread and last-message state |
| Authentication | `sessions`, `password_reset_tokens` | Redis rate-limit/token coordination |
| Media lifecycle | `upload_reservations`, `media_deletion_jobs` | S3 objects and signed/public URLs |
| Async work | `outbox_events`, `processed_events` | Profile propagation, connection email, media metadata; per-consumer deduplication |

Bounded exercise and set arrays from the API are normalized into ordered child
tables. Workout/routine exercises retain immutable exercise-name, muscle-group
and equipment snapshots, so history remains valid when master data changes.

## Integrity and transactions

- UUID primary keys are generated by PostgreSQL; `legacy_mongo_id` columns are
  nullable, unique mapping aids used only by the offline import.
- Foreign keys, unique constraints and checks reject orphaned edges,
  self-relations, invalid counters, duplicate likes/follows and invalid enums.
- Critical multi-table operations use Kysely transactions: workouts plus
  analytics/quota, social edges plus counters/outbox, messages plus
  conversation state, and media reservation/deletion state.
- Partial unique indexes provide idempotency for operation IDs without forcing
  empty/null values to collide.
- PostgreSQL triggers maintain `updated_at` consistently.

## Schema migrations

Migrations are registered in `packages/backend/db/migrator.ts`:

1. `001_initial_postgresql` creates the relational schema, constraints,
   indexes and timestamp triggers.
2. `002_partial_idempotency_indexes` installs retry-safe partial indexes.
3. `003_detached_exercise_snapshots` preserves historical snapshots while
   allowing deleted master exercises.
4. `004`-`013`: body measurements, exercise media paths, locations and
   proximity, follow requests and notifications, story overlays, search
   indexes, story likes, billing retirement (`011` is unused), conversation
   repair. Each is described in [PROJECT_STRUCTURE.md](../PROJECT_STRUCTURE.md) §7.7.
5. `014_outbox_reliability` turns the outbox enums into text with CHECK
   constraints and adds `event_id`, `schema_version`, `correlation_id`,
   `published_at`, the `published`/`dead` statuses and `processed_events`.
6. `015_posts_author_timeline_index` adds the covering index the home feed
   reads per followed author. On a large table build it `CONCURRENTLY` by hand
   first; the migrator runs in a transaction.

Migrations are expand-only: the previous release keeps working against the new
schema during a rollout. Down migrations exist but are a last resort — see
[operations/RUNBOOKS.md](operations/RUNBOOKS.md).

```bash
corepack pnpm --filter @motionmeet/backend migrate:postgres
```

Kysely records applied migrations and serializes concurrent migration runners.
In production a one-shot `migrate` service applies them before the other
services start; the API itself runs with `RUN_MIGRATIONS=false`.

## Offline legacy import

`tools/database-migration` is a separate workspace package and is never loaded
by the API. It streams source collections in bounded batches, upserts by legacy
identifier, preserves relationship mappings and reports the failing collection
and record. Run migration and verification only from an operator workstation
with both source and destination credentials:

```bash
corepack pnpm --filter @motionmeet/database-migration typecheck
corepack pnpm --filter @motionmeet/database-migration migrate
corepack pnpm --filter @motionmeet/database-migration verify
```

Keep the source read-only and take tested backups before importing. Verification
compares record counts, mapping coverage, orphan counts and critical fields.

## Query and capacity rules

- Feed, social, message, story, workout and exercise lists are bounded.
- High-cardinality timelines use stable cursor pagination; compatible offset
  pagination is capped.
- Frequently filtered foreign keys and `(owner, created_at, id)` access paths
  have composite indexes.
- Expensive workout charts read maintained daily aggregate tables.
- Caches are owner-addressed (one Redis hash per member/profile, dropped with
  one `DEL`; no prefix scans). Writes that narrow access drop both members'
  entries or bump the feed audience epoch (ADR 004). Redis failures fall
  through to PostgreSQL.
- The home feed is read audience-first (viewer, followees, connections → each
  one's newest posts on `posts_author_timeline_idx`), so its cost follows the
  audience size rather than the size of `posts`. Plans for both feeds:
  `scripts/load/explain-feeds.sql`; synthetic production-shaped data:
  `scripts/load/seed-synthetic.sql`.
- Validate production-shaped queries with `EXPLAIN (ANALYZE, BUFFERS)` and add
  indexes from measured plans, not speculation.

## Message sync (migration 016)

| Object | Purpose |
| --- | --- |
| `conversations.last_seq` | Last sequence number handed out in the conversation (to a message or a deletion) |
| `conversations.tombstone_floor_seq` | Tombstones up to this number have been purged; a sync cursor below it must resync |
| `messages.seq` | Position in commit order, assigned by trigger `messages_assign_seq`; unique per conversation (`messages_conversation_seq_idx`) |
| `messages_unseen_seq_idx` | Partial index (`WHERE NOT seen`) for the partner's read position |
| `message_deletions` | One tombstone per deleted message (`change_seq` from the same counter), written by trigger `messages_record_deletion`; kept 30 days; no foreign key |

See docs/architecture/adr/005-message-sync.md.

## Comment idempotency (migration 017)

`post_comments.operation_id` (nullable, client-generated) with the partial
unique index `post_comments_user_operation_idx (user_id, operation_id) WHERE
operation_id IS NOT NULL`: a retried comment with the same id is the same
comment. Comments from clients that send no id are unaffected.

## Retention

Scheduled tasks (`packages/backend/workers/cronJobs.ts`, each under an
advisory lock, in SKIP LOCKED batches). Periods are constants at the top of
that file.

| Data | Kept | Task (schedule) |
| --- | --- | --- |
| `sessions` expired or revoked | 7 days after expiry / revocation | `expired-sessions` (hourly, :07) |
| `password_reset_tokens` | until expiry; used tokens 1 day after use | `password-reset-tokens` (hourly, :37) |
| `notifications` that were read | 180 days after creation (unread ones are kept) | `notifications-retention` (daily 04:53) |
| `user_locations` coordinates | 30 days without a refresh, then reset to the pre-fix placeholder (0/0, no accuracy, no city, epoch); settings stay (D-07) | `stale-location-wipe` (daily 05:13) |
| `message_deletions` tombstones | 30 days (D-06); orphans removed; floor recorded | `message-tombstone-retention` (daily 04:23) |
| expired `stories` | until expiry (+ up to 5 min) | `expired-stories` (every 5 min) |
| abandoned `upload_reservations` | until expiry | `abandoned-uploads` (every 15 min) |
| `usage_counters` | until expiry | `expired-usage` (hourly, :17) |
| delivered outbox / processed events | 7 days | `event-history-retention` (daily 03:41) |

Nearby also stops listing a fix after 7 days without a refresh and shows
other members' `lastActiveAt` only to the hour.
